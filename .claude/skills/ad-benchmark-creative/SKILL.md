# Ad Benchmark → Creative

競合広告の実データを起点にMORUの広告を設計する。
**思いつきでクリエイティブを作らない。市場で実際に回っている型を読んでから作る。**

このスキルは `ops/research/`(何を売るか)と対になる。こちらは**どう売るか**を決める。
入口はどちらも競合分析なので、`ops/research/sites.md` のサイトDBと
`ops/ads/benchmarks/` のブランドDBは相互参照すること(Kocolは両方に登場する)。

## 前提として必ず読むもの

- `docs/00_brand_master.md` v0.2追補 — Pet-first, Interior-always / Values / 商品4階層
- `docs/01_brand_guidelines.md` — 9色パレット / 写真4原則 / 禁止表現
- `docs/brand/reference-sheets/` — ビジュアルの正
- `ops/ads/benchmarks/` — 過去の分析結果(取得日を確認。3ヶ月以上前なら取り直す)
- `references/adwhispr.md` — ツールの使い方・ハマりどころ
- `references/translation-rules.md` — 借りる/捨てるの線引き

## ステップ1 — ベンチマークを決める

2通りある。

**指名する**: 狙いを定めたブランド名かURLがある場合。オーナーから渡されることが多い。

**探す**: `find_competitors` を使う。**MORU自身がAdWhisprに登録されていることが前提**
(未登録だと「何を売っているか教えて」で止まる)。`get_my_brand` で確認し、
未登録なら `save_my_brand` する。登録内容は docs/00 v0.2 に沿って:
ペットと人が一緒に暮らすインテリアブランド / Hero商品はフラワーラウンジ(花びら型の猫ベッド) /
日本市場 / 想定客は25〜40歳・都市部・猫と暮らすデザイン感度層。

**領域ごとに1つずつ持つ**のが望ましい。MORUの場合は最低2つ:
- インテリア側のベンチマーク(現在: Kocol)
- ペット側のベンチマーク(現在: Desk Nest Cat Bed)

**ブランド追加は1日3件が上限。** 使い切ると翌日まで追加できないので、
追加前に必ずオーナーに確認する。削除しても枠は戻らない。

## ステップ2 — 全体像をつかむ

`add_brand` → `get_brand_stats`。

見るのは5つ。**稼働本数 / 最長稼働日数 / 推定出稿額 / フックの分布 / フォーマットの分布。**

ここで**相手の成熟度を判定する**。これが以降の扱いを決める。

| | 完成型 | 探索型 |
|---|---|---|
| 例 | Kocol(44本 / 125日 / $241k〜) | Desk Nest(19本 / 53日 / $17k〜) |
| 意味 | 勝ちパターンを掴んで予算を突っ込んでいる | まだ勝ち筋を探している |
| 使い方 | **型を借りる相手**。回っている構造は信頼できる | **言葉とフックを盗む相手**。何を試しているかを見る |

フック分布は最重要の情報。ペット領域は問題提起型が68%、インテリア領域は
カテゴリ紹介中心で問題提起は稀、という違いが実際に出た。
**空いているフックは狙い目**(Kocolは問題提起型を1本しか使っていない = そこが空いている)。

## ステップ3 — 個別の広告を読む

`get_brand_ads` を **`sortBy: longevity`** で取得する。

**稼働日数が唯一の信頼できる勝ち指標。** performance score は全広告同一の既定値なので使わない。
推定出稿額も幅が広く、桁感の参考程度。

読むのは4つ。

**見出しの型** — どういう構造の一文か。「〇〇特集」なのか、問題の名指しなのか、逆張りなのか。

**コピーの構造** — 問題を書いてから商品に繋ぐのか、いきなり商品なのか。長さ。絵文字。

**商材と価格帯** — 何をいくらで売っているか。ここが商品選定と値付けの材料になる。

**オファーの有無** — 割引を使っているか。Kocolは使わずに4ヶ月回している。

**分類ラベルは鵜呑みにしない。必ずコピー本文を自分で読む。**
実例: Kocolは5本が problem_agitation と分類されたが、本文を読むと本物は1本だけだった
(「寝苦しい夜とは、もうサヨナラ。」)。残りは単なるカテゴリ紹介。

同一フックが最長稼働の上位を占めていたら、それが**そのブランドの答え**。
実例: Desk Nestの53日稼働2本はどちらも "No more paws on your keyboard."

## ステップ4 — 勝ちパターンを言語化する

一文で言えるまで圧縮する。言えなければまだ読めていない。

- Kocol = 「テーマで束ねる特集型・割引なし・静止画の商品カット」
- Desk Nest = 「単品×フック反復テスト・問題提起68%・キーボードの上の肉球問題」

**経済的な理由も併せて言語化する。** 型には理由がある。
実例: Kocolの特集型は単なる表現ではなくAOVを上げる装置。
安い商品(限界利益¥1,100前後 → CPA上限¥800)は単品広告では成立しないが、
特集で複数点購入させればAOV¥8,000〜10,000に乗る。
**理由が分かると、MORUで使えるかどうかを自分で判断できる。**

ここまでを `ops/ads/benchmarks/{brand}.md` に**取得日付きで**保存する。

## ステップ5 — MORUに翻訳する

**このステップを飛ばすとブランドが壊れる。** 借りるものと捨てるものを明示的に分ける。
詳細は `references/translation-rules.md`。要点だけ:

**借りる** — 構図 / フックの型 / 訴求の順序 / 束ね方 / フォーマットの選択

**捨てる** — 競合のトーン(高彩度・煽り・大きな文字焼き込み) /
期限付き割引訴求 / パレット外の色 / MORUの禁止表現に触れるもの

**そのまま使えるものがあれば見抜く。** 実例:
Desk Nestの "Your pet doesn't care what their bed looks like. You do." は
MORUのv0.2感情価値(「ペットと近くにいたい。でも自分の生活空間も大切にしたい」)と同一。
競合は単品の売り文句として使っているが、**MORUはブランド宣言として使える**。
こういう一致を見つけたら最優先で使う。

## ステップ6 — 広告商品を決める

**Shopifyの実在庫から選ぶ。** 想像で決めない。`search_products` で status:active を取得し、
価格・在庫数・tierタグを確認する。

判断基準:
- **市場実績で裏が取れているか**(Kalodata等の競合実績、または自社の販売実績)
- **価格帯が競合レンジ内か**
- **在庫が足りるか** ← 見落としやすい。CPA¥2,500で回すと数日で切れることがある
- **商品説明がブランドの声で書けているか**(広告のフックとLPが一致するか)
- tier-aov の安い商品は**単品広告では成立しない**。特集型で束ねる

決めたら、その商品に紐づく実物写真を取得する(次ステップのリファレンスになる)。

## ステップ7 — クリエイティブを作る

### 画像生成プロンプト
`image-prompt-director` スキルと `references/moru-notes.md` に従う。必須事項:

- **実物商品写真をリファレンスに渡す**。冒頭に形状ロック
  (`reproduce faithfully / do not redesign, restyle, resize or alter`)
- **文字を焼き込まない。** 日本語は生成AIで崩れる。見出し用の余白(negative space)を構図に確保し、
  文字は後からデザインツールで載せる
- 差し色は1画面1〜2色。署名は MORUブルー #1E5B8F × テラコッタ #D65832
- サムネイルは白抜き背景にせず、明るい生活シーンの中の商品にする
- 同じ商品で**構図とフックを変えた複数バージョン**を作る(Desk Nestのテスト構造の再現)

既知の失敗と対処は `references/creative-pitfalls.md` を必ず読む。

### 見出し・本文・説明(Meta動的クリエイティブ)
`references/copy-rules.md` に従う。要点:

- 見出し5・本文5・説明5。**5つを同じことの言い換えにしない。角度を変える**
  (逆張り / インテリア問題 / 共生 / 機能 / 商品そのもの)
- 組み合わせはランダムに入れ替わるので、**それぞれ単独で成立**させる
- 本文は冒頭125字ほどで折りたたまれる。1行目に結論
- 説明はInstagramでは表示されないことが多い。重要情報を入れず、空欄にもせず、事実の補足

## ステップ8 — 記録する

- `ops/ads/benchmarks/{brand}.md` — 分析結果。**必ず取得日を書く**
- `ops/ads/creatives/{product}.md` — 採用プロンプト、見出し・本文、
  **没にしたものと理由**、生成の失敗と原因
- 新しいベンチマークブランドは `ops/research/sites.md` のサイトDBとも突き合わせる

**失敗の記録が最も価値がある。** 次に同じ罠を踏まないための資産。

## 鉄則

- 稼働日数以外の指標を勝ち指標として使わない
- 分類ラベルを読むだけで済ませない。コピー本文を読む
- 借りる/捨てるを分けずにTTPしない
- 実物写真をリファレンスに渡さずに商品画像を生成しない
- 在庫を確認せずに広告を回さない
- 分析に取得日を書かずに保存しない
- ブランド追加(1日3件上限)を確認なしに消費しない
